= Atrium 0.5.21 — Life 0.5.95 public gateway compatibility
:toc:

== Upstream producer contract
Life 0.5.95 declares `GET /looprd/the-life-loop/v1/play/info` as the public capability envelope and `POST /looprd/the-life-loop/v1/play` as a Life-authenticated game-scoped command endpoint. The backend is operator-provisioned, so source availability is not live deployment proof. The game engine and match seats remain exclusively Life-owned.

== Consumer mapping
* The reviewed and available Life discovery instance supplies the LoopRD component API base. `atriumd.yaml` does not supply an absolute game server URL.
* Public `GET /play/info` does not require an actor game bearer. Subsequent `POST /play` operations require an independently verified `life.loop` bearer. No Social credential is passed to a game iframe, URL, or Tavi.
* Live `create(settings, requestId)` now requires a stable request ID and `ruleset: classic` alongside `mode: private-async` and `deadlineHours: 60` or `null`. The caller MUST derive `requestId` deterministically from a trusted, stable challenge or match-creation intent; retry with the SAME ID. Never generate a fresh ID on retry.
* Existing mock lobby behavior is maintained separately for sandbox tests; the live lobby is never silently replaced by a mock.
* `invite`, `join`, `resume` and `list_matches` use Life's existing match projections. Atrium never creates a match when notified that a Tavi challenge was accepted; the authorized creator explicitly invokes Life `create` once. An invitation `join` must return that match ID.
* LoopRD HTTPException `detail` and transport 401/403/404/409/422/503 failures are surfaced as errors, not successful game results. Actual production HTTP status handling depends on the injected request transport preserving status and detail.
* Hosted launch defaults to the external browser. Opaque match IDs are only navigation context, never authorization. Life independently verifies the current viewer upon resume.
