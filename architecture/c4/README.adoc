== Scope and authority

`architecture/c4/workspace.dsl` is the machine-readable, project-owned C4 architecture model. This AsciiDoc is its evidence and interpretation companion. It starts at *C4 Level 3*: the Atrium LoopRD component, standalone web portal, and TaviX extension each have component diagrams. Minimal system-context and container diagrams locate those components; two dynamic diagrams document a deployment-dependent discovery flow and a *source-only* Checkers flow.

Only Atrium-owned source is decomposed. Tavi Messenger, Tavi Social, LoopRD/DAPI, and independent game services are represented as external software systems. No private Social implementation, infrastructure, account database or external game internals are inferred. There is no deployment diagram: the actual operator TLS proxy, published TaviX release, deployed DAPI version, game launch bindings, and live network topology have not been verified from this source ZIP.

This is an *architecture baseline*, not a claim that every modeled source-level component is running. The `SourceOnly` tag marks components and stores which are implemented/tested in source but **not connected to production LoopRD game routes**. Static source configuration with empty catalog URLs is not evidence of a deployed public catalog.

=== Persistent storage boundaries

* `registryStore` — SQLite schema v6 is defined in root `looprd.yaml` and managed through the DAPI runtime. Publisher, candidate, trusted-instance and receipt records are Atrium-owned.
* `marketStore` — independent Market Grove child uses its own LoopRD SQLite database. Market Grove is *not* the Atrium registry and is not a Tavi Wallet integration.
* `checkersStore` — `checkers_matches` and `checkers_requests` are created by the source-only `CheckersMatchAuthority` SQLite implementation. This is not a deployed production table in the root LoopRD schema.
* `lobbyStore` — the local source-only hostless lobby and outbox SQLite implementation; production authentication and route activation remain pending.

== Architectural relationships and protocols

* DAPI executes the Atrium `looprd/v1` component, including registry/discovery handler fragments. `modules/registry`, `modules/arcade` and `modules/games/checkers` are **includes within one Atrium component**, not independently deployed DAPI components. Market Grove is explicitly a `subcomponents` child with separate game-owned state.
* The `atriumd/v1` sidecar contains a portable `component` and game metadata, with no deployment URL, auth secret or operator-managed `launchOrigins`. Operator trust bindings supply those addresses after verification (`src/atriumd_contract.py` and `src/discovery_v2.py`).
* The hosted catalog projection reads current `AtriumTrustedInstance` and `AtriumTrustedDeployment` rows, permits only active Git-backed releases with valid HTTPS bindings, and emits `atrium.hosted-games/v1`. In 0.5.64, `web/hosted-config.json` is not bound to a live gateway. The LoopRD hosted handler requires runtime support and deployment verification; source presence does not establish public availability.
* Reviewed web apps are fetched through a configured catalog and SHA-256 validated, sandboxed iframe. This is **not** a trusted OAuth, publisher-signature or session handoff (`src/apphost.mjs`).
* `CheckersSocialAdmission` requires injection of trusted `resolve_session`, original challenge lookup and `accepted_contact` callbacks; no HTTP client can supply an identity or an accepted challenge itself. `CheckersMatchAuthority` owns SQLite revisions and game transitions. The game rules are implemented by the Checkers engine, not generic Atrium/Tavi UI.
* `src/checkers_remote_client.mjs` is transport-injected; the browser Checkers player requires an independently secured same-origin API. Neither the player nor the Tavi extension contains an authoritative game server. Actual Social and protected Checkers production routes remain outstanding.

== Important dynamic workflows

=== Discovery to hosted catalog (conditional runtime configuration)

`atrium_discovery_flow` describes the implemented *contracts and code path*, not verified live deployment. The operator reader collects inventory and sidecar, the Atrium trusted discovery receiver stores the candidate and binding, and a separately configured hosted catalog handler safely projects only active trusted game instances. A discovery observation by itself does *not* publish a game: operator trust and valid binding are required.

=== Accepted challenge to Checkers turn (source-only)

`atrium_checkers_source_flow` illustrates the tested trusted adapter path. The host must resolve a real Social account and original accepted challenge before invoking match operations. The dispatcher never accepts client-provided identity as authority. Revision, move validation, idempotency and state write happen server-side. **This dynamic view is not a live Tavi-to-browser acceptance result.**

== Validation and maintenance policy

The model was derived from the 0.5.64 source ZIP and added in 0.5.65. Its local regression guard (`tests/test_c4_architecture.py`) checks required views, referenced source paths, stable key names and source-only boundaries. This is **not equivalent** to parsing or validating the DSL using the official Structurizr CLI. Run the CLI where available:

[source,shell]
----
structurizr validate -workspace architecture/c4/workspace.dsl
----

Or, with the official Structurizr CLI distribution, use the documented `validate -workspace` command. Record actual CLI output in a later pass when available; do not infer it from this source-only check. Consult https://docs.structurizr.com/dsl/language and https://docs.structurizr.com/cli/validate for syntax and invocation.

For later development: update DSL and this README **in the same pass** when a component, responsibility, dependency, transport interface, persistence boundary or deployment architecture changes. Keep IDs stable and distinguish deployed from source-only status. Reference ODPS capability names, if a compatible Atrium ODPS description becomes available, rather than copying unrelated product descriptions into C4. No Atrium ODPS artifact was present in the inspected source ZIP.

Do not add a deployment diagram until actual runtime nodes, HTTPS proxy, published catalog mapping and game host bindings are verified; do not model hypothetical infrastructure as running.

== Offline candidate ingestion (0.5.68)

The new `offlineCandidateTools` Python CLI container owns `offlineBundlePackager` and `offlineBundleValidator`. It reads third-party local web builds, writes deterministic candidate ZIPs and enforces offline, hash, path and size constraints. Its new view key is `atrium_offline_candidate_components`. **It does not install anything in Tavi, talk to LoopRD, publish a catalog or establish a local game inventory.** See `docs/OFFLINE_GAME_HANDOFF.adoc`. The separate Tavi/TaviX installed-package inventory and launch contract is pending source verification, so no fabricated dependency was drawn. No independent Structurizr CLI validation is claimed.


== Local TaviX developer-preview conversion (0.5.69)

`offlineCandidateTools` gains `offlineTavixPreview` (`tools/offline_tavix.py`).
It accepts only a verified `atrium.offline-game/v1` candidate and produces a
TaviX 1.0 `tavi.extension/v1` **developer preview** with a per-member SHA-256
lockfile and portable `ui/atrium-game.json` provenance metadata.
The independent game source and game engine are not part of the Atrium source
package. No call from the operator CLI to Tavi or LoopRD occurs.

Tavi's local `.tavix` installer (Tavi 0.3.127+ source) is an *external,*
operator-controlled step. Tavi's sandbox may prevent localStorage/IndexedDB,
and a local preview is not a trusted or publicly released extension.
The ATR-171 installed-game inventory/identity-based local launch path is still
**unimplemented**. The converter does not create a relationship between
Atrium's live catalog and Tavi's installed-package registry.

See `docs/P1_113_KLONDIKE_EXTERNAL_GAME_QA_069.adoc` and
`docs/OFFLINE_GAME_HANDOFF.adoc`. The C4 source regression is **not equivalent**
to an official Structurizr CLI validation.

== Embedded player shell (0.5.76)

`portalShell` now owns the shared storefront and embedded Tavi player-first view: My Games and Discover are compact secondary tabs; unconnected Activity and Lobbies placeholders remain standalone-only. Tavi remains the only global navigation owner. No new external interface or claimed host theme API is introduced. The separate 1.0.7 developer preview requires local operator install; the 1.0.4 immutable extension remains untouched. See `docs/ATRIUM_TAVI_EMBEDDED_UX_076.adoc`.

== Empty bundled catalog snapshot (0.5.78)

`src/hosted_catalog.mjs` treats an empty operator `gatewayUrl` as a request
to read the bundled, validated `web/hosted-games.json` snapshot. `web/main.mjs`
consumes it using the existing hosted catalog client; no additional remote
server or dependency is implied. An empty published catalog is a healthy
zero-item UI state. Configured remote failures remain visible and fail closed.
See `docs/ATRIUM_CATALOG_HEALTHY_EMPTY_078.adoc`. The existing C4 components
and opaque optional gateway boundary remain unchanged.
